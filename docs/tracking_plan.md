# Proposed instrumentation and linkage

These events do not exist in the public dataset. They require operator engineering, privacy review and verification against a rental ledger before the trial. Collect pseudonymous operator account IDs only where necessary for persistent assignment and linkage; never attempt to re-identify public trip data. Do not collect raw addresses, precise continuous location or contact lists. A saved station pair is sufficient for this proposal; document retention, deletion and permitted access with the operator before implementation.

## Common envelope and rules

All events: `event_id` (UUID, generated once and reused on retries), `event_name`, `schema_version=1`, `occurred_at_utc` (source event time), `received_at_utc` (server ingestion), pseudonymous `account_id`, session ID if applicable, `intent_id` where relevant, app version/platform, `experiment_id`, persistent `assignment_id`, variant and assignment timestamp. Anonymous events cannot silently acquire assignment from a later device. Server ledger events use server clocks. Client clock offset and offline delay are recorded; quarantine implausible ordering rather than silently switching to upload time.

Deduplicate on event_id; rental linkage also checks operator transaction ID. Same event ID with conflicting payload is an error, not last-write-wins. Assignment is a server event with one unique account/experiment record. Exposure is a rendered interface event, delivery a provider-confirmed push event, engagement an explicit interaction: they are different denominators. A failed exposure still belongs to ITT.

| Event | Trigger | Required event-specific properties | Identity, validation and timestamp semantics |
|---|---|---|---|
| `experiment_assigned` | Server first accepts an eligible intent, before response renders | eligibility version and pre-treatment fields, randomisation stratum, allocation version, experiment/variant | Unique account+experiment; immutable; server event time; check 1:1 aggregate balance and no reassignment |
| `departure_intent_recorded` | Neutral confirmation of plan to leave within 15 minutes | intent_id, saved_pair_id, preselected origin/destination station IDs, acceptable types, max walk band, confirmation version, eligibility decision/reasons | One intent per confirmation; merge retries, suppress new eligible intent within 30min; event time precedes any treatment exposure |
| `station_status_viewed` | Status card actually renders and is visible | station_id, count/type payload, operational flags, feed timestamp, station report timestamp, retrieval time, render time, source, surface, payload ID | Dedup event_id; multiple genuine views permitted; ages computed at render (not fetch); require count nonnegative or explicit unknown, flags and station IDs valid |
| `alternative_station_suggested` | An acceptable alternative is rendered | suggestion_id, origin station, alternative station, rank, algorithm version, bike type, walk-distance estimate/band, return constraints, status payload ID/ages | Unique intent+suggestion+render instance; reject origin=self, invalid station, duplicate ranks; record estimate source, do not call estimated distance actual walking |
| `alternative_station_selected` | Rider explicitly selects an alternative | suggestion_id, chosen station, interaction type, preceding suggestion event reference | Event ID dedup; must reference earlier suggestion for same intent/account; selection does not imply arrival or rental |
| `availability_alert_delivered` | Provider confirms push delivery, in a future alert trial | alert_id, saved schedule, scheduled send time, provider delivery time, permission state, payload ID, destination device pseudonym | alert+device dedup; separate enqueue, send, provider acceptance, delivery and opened events; provider acceptance alone is not confirmed delivery; unknown receipt marked unknown |
| `rental_started` | Operator ledger confirms rental start | rental_id, bike type, start_station_id nullable, rental start time, test/void flag, ledger version | rental_id unique; ledger event time; link account to assignment and eligible intent only via authorised operator IDs; success window uses original intent clock |
| `rental_returned` | Ledger confirms rental end | rental_id, end time, station_id nullable, dock/rack return type, confirmation state | Dedup rental_id+ledger_version; end≥start, known timezone; return is distinct from failed-dock attempt; rack return cannot be assumed a dock success |
| `journey_feedback_submitted` | Rider submits an optional post-intent survey | invitation_id, intent_id, questionnaire version, usefulness, alternative suitability, detour/failed-return answers | One response version per invitation; retain amendments explicitly; measure invitation/response rates by arm; avoid free-text personal data where structured answers suffice |

## Measurement quality contract

Join assignment→intent→rental on authorised stable account linkage, not name, coordinates or fuzzy timestamps alone. For primary first intent, rental start falls in the 15-minute window and matches a preselected acceptable type. If several starts occur, outcome is binary one; one rental cannot credit overlapping intents. Keep non-station rentals if eligible; a missing station ID is not a missing rental. Reconcile counts and transaction states to the complete rental ledger, log late arrivals, voids and corrections, and freeze the analysis ledger version. An event missing from an app log does not prove there was no rental.

Cross-device: authenticated accounts share assignment, but logged-out sessions and multiple accounts may prevent linkage. Do not fingerprint devices to repair identity. Quantify unresolved linkage by arm; test differential event loss and instrument delays, and use bounds/sensitivity instead of a confident complete-case result. Consent withdrawal follows policy and is recorded as unresolved where applicable. Analyse only mature event windows; no-rental after an immature follow-up is unknown.

Validate schemas at ingestion with versioned required fields, enums, nullable reasons, ID referential integrity, timestamp bounds, retry deduplication and assignment-before-exposure checks. During a blinded A/A instrumentation pilot, verify assignment stability across devices, known test journeys, payload freshness, intent deduplication, server/client clock offsets, ledger reconciliation and alert state distinctions. Require at least 99% assignment/outcome-linkage completeness and investigate arm imbalance before efficacy testing. This is a proposed acceptance gate; no current claim of achieved tracking quality.
